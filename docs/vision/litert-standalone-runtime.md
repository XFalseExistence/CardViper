# Standalone LiteRT Runtime Checkpoint

This B4 checkpoint pins the standalone Android dependency to
`com.google.ai.edge.litert:litert:2.3.2` from Google Maven. The app's current
minimum SDK is 26. Google's Android release table lists API 23 for LiteRT
2.3.2, while the resolved 2.3.2 AAR manifest declares minSdkVersion 24; the
actual artifact floor is therefore API 24. No Play Services, GPU, NPU, model
download, or production model asset is enabled here.

The implementation uses the CPU `Interpreter` API exposed by the standalone
2.3.2 package. LiteRT recommends `CompiledModel` for new inference code, but
the current injected `LiteRtRuntime` boundary receives in-memory model bytes
and must report actual tensor names, shapes, and dtypes. The documented
`CompiledModel` Android entrypoints load from an asset manager or filesystem
path and use LiteRT `TensorBuffer`s. The Interpreter API accepts a `ByteBuffer`
and exposes the required tensor metadata directly. This is adapter scaffolding;
no production model is loaded, and this API choice must be revisited before
production inference is enabled.

The Android test fixture
`app/src/androidTest/assets/vision/litert_runtime_smoke.TEST_ONLY.tflite` is a
deterministic 892-byte arithmetic graph (`input * 2`). It has no card
classification or detector semantics. Its metadata sidecar is generated by
LiteRT inspection and records its tensor signature and SHA-256. Rebuild it
with TensorFlow 2.16.2 and the `ai-edge-litert==1.0.1` inspector from the
repository's `train` extra:

```sh
python ml/tools/generate_litert_runtime_smoke.py
```

The Android instrumentation test validates the model hash and observed
signature, executes known float input values through the real Android runtime,
checks the exact doubled output, and checks that a closed session rejects
inference. The synthetic fixture is not a model-accuracy or production
inference test.

The pinned Android 2.3.2 AAR contains `libLiteRt.so` for `arm64-v8a`,
`armeabi-v7a`, and `x86_64`; each binary's ELF `LOAD` segments were inspected
and use `0x4000` alignment. APK ZIP alignment is checked separately with
`zipalign -c -P 16 -v 4`. Device execution is required to establish runtime
behavior on a device; APK alignment alone does not prove that.

The 2.3.2 AAR has no 32-bit `x86` LiteRT binary. Its supported packaged
runtime ABIs are `arm64-v8a`, `armeabi-v7a`, and `x86_64`; do not instantiate
this runtime on x86 until the app's ABI policy is resolved. The application
has not changed its ABI filters in this checkpoint.
